# Home Assistant on hass-pi

Home Assistant Core runs as a standalone NixOS container on hass-pi (Raspberry
Pi 5), built centrally by container-factory and pulled nightly by the
container updater (ADR-002, see CONTAINER-HOST-SETUP.md). The old Home
Assistant OS install was retired on 2026-10-20; its last backup was restored
into this container. Everything below is declarative unless marked **state**.

## Where things are

| What | Where |
|------|-------|
| Container preset (components, HA config, dashboards, backup item) | nix-presets `containers/home-assistant.nix` |
| Host wiring (container, DNAT, firewall, host-side services) | `hosts/hass-pi/default.nix` |
| Data dir (**state**: `.storage`, recorder DB, secrets) | hass-pi `/var/lib/home-assistant` (impermanence bind mount, uid 286) |
| ESPHome device configs | `hosts/hass-pi/esphome/*.yaml` → linked into `/var/lib/esphome` |
| Authentik application (OIDC) | nix `infra/authentik.tf`, `local.oidc_apps.home-assistant` |
| Health check | core-pi gatus, group Apps |

## Reaching it

- `https://hass.kleinbem.dev` — Caddy on core-pi, NetBird/LAN only (not on the public tunnel). HA's `trusted_proxies` in the preset must list every Caddy address or HA answers 400.
- `http://10.0.0.21:8123` — the host DNATs its LAN port to the container (nftables in `hosts/hass-pi/default.nix`). This is also HA's `internal_url` (preset option `lanUrl`), which the companion app uses on the LAN.
- Login: local owner account `martin` (break-glass, keep it) or **Sign in with Authentik** (`auth_oidc` custom component, public PKCE client, staff group = HA admin). Authentik creates its own HA user on first login; the two are not linked on purpose.

## Updating

Nothing to do by hand. nixpkgs → lock bot (03:00 UTC) → build-all → promote-production publishes the container manifest → hass-pi pulls at 03:13 local. A failed x86 build-all leg blocks the manifest for every system. The host itself auto-upgrades at 04:29 local (`nixos-upgrade`), which does **not** refresh containers.

Component deps are baked into the image: adding an integration means adding it to `extraComponents` in the preset (HA Core on NixOS cannot pip-install). Custom components come from `pkgs.home-assistant-custom-components` (alarmo, auth_oidc, ha_mcp_tools), lovelace cards from `pkgs.home-assistant-custom-lovelace-modules` (button-card at `/local/nixos-lovelace-modules/`). No HACS.

Version pins that must go away eventually (both commented in the preset): paho-mqtt tests skipped; **pywizlight pinned to 0.6.3** (nixpkgs ships 0.6.6, HA still requires 0.6.3; upstream draft NixOS/nixpkgs#576178).

## AI agents

The `ha_mcp_tools` custom component runs the HA-MCP server inside Home
Assistant (87 tools). Set it up once in the UI (**state**): a dedicated local
admin user, then *Add Integration → HA-MCP Server*, remote access in
*Secret URL* mode. The connect URL goes into `kleinbem-secrets`
`nix/per-host/nixos-nvme.yaml` as `ha_mcp_url`; `modules.mcp.homeAssistant`
(nix-presets `mcp.nix`) bridges it into every MCP client on the workstation
via mcp-proxy. The upstream Home Assistant agent skills
(`homeassistant-ai/skills`) are fanned out by `modules/home-manager/ai-agents.nix`.

## Restoring / moving the data dir

The HAOS backup format is just the `/config` directory. To restore one into
this container: stop `container@home-assistant`, move the *contents* of
`/var/lib/home-assistant` aside (it is a mount point, it can't be renamed),
extract the backup's `homeassistant.tar.gz` `data/` there, drop
`configuration.yaml` (generated by Nix), `custom_components/`, `.storage/hassio`
and any Supervisor-only config entries, `chown -R 286:286`, start. HA migrates
`.storage` and the recorder DB forward on first start. A dry run on the
workstation works with the same package plus the module's PYTHONPATH
(`systemd.services.home-assistant.environment.PYTHONPATH`); the bare
`bin/hass` wrapper does not carry the component libraries.
